# Decisions

D1. No vector RAG. A full class transcript (~15-25k tokens) fits in one LLM call and there are only 10 labelled classes, so there is nothing to retrieve at scale. Possible Phase 2 extra: show the judge the nearest labelled classes (by stats) as calibration examples, evaluated leave-one-out.

D2. Hybrid pipeline: code measures what it can measure reliably (stats, frames), the LLM judges against a rubric derived from organiser feedback and must cite timestamped quotes, quotes are verified in code, and a fixed formula produces the label. Explainable and testable; no training on 10 samples.

D3. Transcription: a provided Zoom VTT is used directly (exact speakers, instant). Otherwise whisper.cpp runs locally, so audio never leaves the server. Model choice depends on 2-thread benchmark (pending).

D4. LLM judge: DeepSeek (deepseek-flash by default) via its OpenAI-compatible API. DeepSeek's privacy policy lists model training as a purpose and stores data in China, so only pseudonymised transcript text and numeric features are sent. Frames are never sent, even though deepseek-flash accepts images.

D5. UI: Streamlit, hosted as a Docker Hugging Face Space (large uploads, ffmpeg, compiled whisper.cpp, secrets).

D6. Labels: weak and quality issue both map to Poor; quality issue also raises a technical flag.

D7. Thresholds and weights start from the rubric and are checked on the labelled set, not fitted to it (2 samples per level would overfit).

D8. Face detection: OpenCV 5 removed CascadeClassifier, so we pin opencv-python-headless<5 and use FaceDetectorYN (YuNet ONNX, ~230 KB, downloaded at setup), which also handles small faces in Zoom gallery tiles better than Haar.

D9. DeepSeek thinking mode disabled for the judge (JUDGE_THINKING=disabled). The docs say thinking is on by default and that temperature is ignored in thinking mode, and they do not document JSON output together with thinking. Non-thinking mode keeps temperature control, keeps reasoning tokens out of the max_tokens budget and returned valid JSON first time on every Phase 1 call (~8 s for a 20k-token class). Revisit if judgement quality, not format, becomes the bottleneck.

D10. Judge design: direct per-criterion scoring (JUDGE_DESIGN=direct). An extract-then-score variant (LLM reports facts, code maps them to 1-4) separated an excellent and a weak class less well (E9): LLM-reported counts such as praise and negative remarks were unreliable, while yes/no facts (homework assigned, children greeted by name) did discriminate. The facts design stays available for Phase 2 (e.g. yes/no facts as evidence for the direct judge).

D11. Whisper model for the no-VTT path: ggml-base-q5_1 at 2 threads. On a 2-minute English clip it ran at 0.17x real time with 82% word agreement with the Zoom VTT, versus small-q5_1 0.50x / 83% and large-v3-turbo-q5_0 1.05x / 83% at 6 threads (E8). Agreement is with another machine transcript, on one clip; re-check chess terms and Indian-English speech before Phase 2 relies on it.

D12. Label aggregation: problem count (AGGREGATION=problems). Each criterion scored <= 2 is one problem; 0 = Excellent, 1 = Good, 2 = Average, 3+ = Poor; fewer than 3 scored criteria gives a placeholder label with a warning. Chosen because the organiser's labels read as "how many problems did this class have", the weighted mean could not produce Poor on the labelled set (E10), and a count is easy to explain ("Poor: problems with opening, closure and visual presence"). The weighted mean is still reported. The ARCHITECTURE face cap is a warning, not a cap, until screen-share frames are excluded reliably (E6).

D13. Aggregation is frozen; the problem-count rule (D12) stays. Every rule tried gives 3-5/10 exact labels, and dropping communication and technical_quality from the count gives 3/10, so the gaps between rules are run-to-run judge noise rather than one rule being better. Further tuning would only fit noise in 10 classes. The judge already agrees with the organiser on 74% of criterion expectations; what limits the label is signals we do not measure yet (voice energy for communication, the 8x8 background for visual presence), so Phase 2 effort goes there.

D14. technical_quality is scored by code from objective evidence, not by the LLM. The LLM gave it 2 for nearly every class, including both excellent ones (E10), so it added an almost constant problem to the count. Thresholds, fixed now before any results are seen: the class has a technical problem only if there are >= 3 verified connectivity incidents per hour of class, or frozen frames are >= 20% of camera (non-screen-share) frames. Otherwise no technical problem.

D15. A criterion whose scores barely vary across the labelled classes (standard deviation < 0.3) is still shown in the report with its observations, but is left out of the label. A near-constant score cannot tell classes apart; it only shifts every label the same way (communication in E10 is the example: 3 for 9-10 of 10 classes). Re-checked whenever the judge or a scorer changes.

D16. Privacy gate for anything sent to the judge (scripts/leak_audit.py, all classes except the Malayalam demo, whose transcript is ASR noise), both required: (1) zero tokens that fuzzy-match an original display-name token at >= 85; (2) zero human-labelled names left among the 70-84 matches. The 70-84 band is checked against a human review of the matches (.cache/leak_review_labels.json, local only), not failed automatically, because about half of the matches in that band are ordinary words (21 of 37 in the first review); new, unlabelled 70-84 matches must be reviewed before the gate can pass. Documented exception to (2), narrowed in E24: a labelled name that is also an ordinary dictionary word (wordfreq zipf >= 4.0) is accepted only when every remaining occurrence is lowercase, i.e. used as the word; it is reported in its own column. The earlier, wider exception (any word-like labelled name, E11b) let real names through: the review of 22 Oct found 3 more names that are also common words, and their capitalised forms were reaching the judge. In the 70-84 band the scrubber now replaces such a token with [NAME] when it is capitalised mid-sentence, or capitalised at a sentence start and followed by , ? or ! (vocative; the whisper-path rule, so both paths agree), whatever its zipf; otherwise at a turn or sentence start it is kept, so it can still count as a name left. Documented exception (E24): excellent B472, one occurrence at the start of a student turn, which matches the tutor's display-name token, not a child's; it is an ASR-mangled form of the tutor's name rendered as a different name, so it identifies no child. scripts/leak_audit.py accepts it by class and count (DOCUMENTED_EXCEPTIONS, token not written in the repo) and only after checking that the matched display-name token is the tutor's. Display-name tokens that are themselves high-frequency words (zipf >= 4.5, e.g. "Will") count as names only when capitalised, in both the scrubber and the audit (E11c). A failing gate blocks release.

D17. Over-scrub (common English words replaced, as a share of tutor words; target <= 0.5% per class, ASR-noise demo excluded) is a monitored utility metric, not part of the privacy gate. Over-scrubbing damages what the judge sees, so its cost is accuracy, not privacy, and the accuracy metrics already measure that cost. scripts/leak_audit.py reports it alongside the gate; docs/EVALUATION.md lists it as a utility row.

D18. Shipped label rule: severity tiers (AGGREGATION=severity), replacing the problem count of D12 and the freeze in D13. D13 stopped ad-hoc tuning of the count; the severity rule was written from the organiser's wording in docs/EVALUATION.md before any run and kept by the pre-registered keep rule (E16: pairwise 75% -> 84%, run agreement 10/10). It was derived from the notes on the same 10 classes, so its accuracy there is optimistic, and it is harsh (bias -0.80): two of its critical checks rest on measurements known to be weak (screen-share tagging for camera frames, E6; a missed rapport quote turns into a critical problem). The problem count and weighted mean are still reported. Confidence is now the distance to the nearest label boundary (0.75 one finding away, 1.0 two or more; <= 0.25 for unusable input).

D19. Label-free check filter (extends D15): any severity check that fires for >= 80% of the 12 classes (a class fires when the check fires in a majority of runs) is shown in the report but not counted; it cannot tell classes apart. scripts/check_rates.py computes the rates from a measurement pass; excluded check ids go into LABEL_EXCLUDE next to criterion ids. First application (E17): no check reached 80% (highest no_recap 75%), so nothing was excluded. Re-check whenever a check's measurement changes.

D20. A3b is kept although the keep rule rejects it (pairwise 84% -> 75%, E17): it fixed measurement bugs (missing quotes read as "no", whole-frame darkness, mute management counted as connectivity, an unvalidated face tag treated as critical), and a bug is not kept because it scores better. The override is marked in eval/ablations.md. A3b's rapport guard did measure the wrong thing: nearly every class has some greeting, while the organiser's complaint is "hello, then straight into content". Rapport is therefore measured from the warm-up instead (A3c, E18): the judge quotes the first line of lesson content, and code counts the minutes from the first tutor greeting to it and the students who say >= 4 words in that window; "no" if < 2 students or < 2 minutes, "yes" if >= 3 students and >= 3 minutes, else unknown; no verified content start -> unknown. Thresholds fixed before any A3c result.

D21. Final shipped configuration, accuracy work frozen: A3d (E20). Evidence-first judge example (A0), code-scored technical quality with problem phrases only and communication out of the label (A1, A3b, D14, D15), verified three-state facts bounding the opening, engagement and closure scores (A2, A3b), severity-tiered label rule (A3, D18) with rapport measured from the warm-up before the first content line and unknown when no tutor greeting is found (A3c, A3d, D20), face check moderate until the screen-share tag is validated (E6b), lighting from the face box. Keep rule: pairwise 88% vs A3b's 75% (E20). On the 10 labelled classes: exact 5/10, within one 9.7/10, bias -0.53; the rule was written from these classes' notes, so these numbers are optimistic. No further ablations.

D22. A critical problem needs speaker-labelled evidence. On the no-VTT path the "no rapport" fact comes from the judge's own reading of a quote whose speaker is unknown (rapport_method = judge, E25), so it counts as a moderate problem at most, never critical; measured from the warm-up (speakers known) it stays critical. Reason: evidence quality. A critical problem decides the label on its own (Poor), and a quote that cannot be attributed to tutor or child is too weak for that. Found on the live no-VTT test of good B552 (mp4 only): the VTT path gave Good, the no-VTT path Poor, through a judged "no rapport" (E27). Accuracy rules otherwise stay frozen (D21).
